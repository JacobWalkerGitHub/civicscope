# ADR 0001: Foundation choices

Date: 2026-11-02 · Status: accepted

## Decisions

- **Monorepo (pnpm workspaces):** `apps/web` (Next.js public site + admin), `packages/core`
  (domain rules and shared enums), `packages/db` (Drizzle schema, migrations, seeds).
  Validation schemas live in `packages/core` for now; they move to their own package only if
  they grow large enough to need it.
- **MySQL 8.4 + Drizzle ORM:** typed, SQL-transparent; migrations generated by drizzle-kit and
  committed. CI fails if the schema changes without a migration.
- **Rules enforced in the database, not only in code:** foreign keys everywhere; CHECK
  constraints for invariants that can be expressed per row (for example, a race names a party
  only in a partisan primary); the same rules exist in `@civicscope/core` so forms can explain
  errors before the database rejects them.
- **Race copies its election's type and primary system** through a composite foreign key, so
  the party rule can be a CHECK. Consequence: an election's type cannot change once it has
  races; that is intended.
- **Race uniqueness uses a generated `contest_key`**, because MySQL unique indexes treat NULL
  district/party values as distinct.
- **Audit log is append-only via triggers.** RDS requires `log_bin_trust_function_creators = 1`
  in the DB parameter group for the migration user to create triggers; local Docker and tests
  set the same flag. The app's database user will additionally have no UPDATE/DELETE grant on
  `audit_log` (Phase 1).
- **Hosting:** ECS Fargate + RDS, defined later with AWS CDK. To keep costs low: one small
  Fargate task, public subnets (no NAT gateway), single-AZ RDS until launch.
